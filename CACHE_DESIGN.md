# Reader cache foundation

## Behavior and boundaries

- The portal transport keeps up to 64 MiB of disposable public JSON responses in Android's cache directory. Entries are keyed by the complete URL and HTTP variation metadata; the exact PostgREST resource and projection must be allowlisted. Blogs and comments must explicitly request published rows. Search-text queries, POST/RPC calls, profiles, session data, account-specific results, mutations and requests with cookies/range headers are not admitted. All other requests are marked `no-store` so the HTTP cache cannot accidentally persist them, even if a server returns an overly permissive header. Cacheable reads are sent anonymously, not under a reader's identity.
- A hit returns immediately, even offline. A separate anonymous check runs at most once per URL per ten minutes while the app is active. The last good entry remains on network or server failure. A successful changed response replaces it; 401/403/404/410 and responses that forbid reuse evict the old entry. The server's `no-store`, `no-cache`, `private`, `must-revalidate`, zero max-age, unsafe cookies and `Vary: *` are respected. A cached result is never proof that a remote update or deletion has not occurred while offline. On-screen home and article content can refresh after a completed check; other views pick up refreshed entries when loaded again. Pull-to-refresh permits an immediate background check.
- `PublicCacheWarmWorker` uses WorkManager with unmetered-network and battery-not-low constraints, also checking for Wi-Fi before each batch item. It warms home metadata, up to 12 recent/featured article bodies and 30 image URLs. It does not download PDF files, audio or video. WorkManager is opportunistic: Android may defer or stop it. An in-flight request can finish after the connection changes. Images with query strings or URL credentials are not preloaded.
- Coil's existing expendable image cache is 250 MiB; the existing Media3 stream cache is 256 MiB. Automatic speculative music-byte prefetch is disabled; played bytes may still be cached. Existing explicit music downloads and PDF download/open mechanisms remain separate. Previously opened PDFs may be available offline while their cached file survives. Explicit downloaded media can consume more space and isn't covered by the 64 MiB JSON budget. The OS may delete any cache at any time.
- Settings' existing clear-cache action now also evicts the public JSON and reference-memory layers. Active screens or workers may fetch again afterwards; this is not an erasure tool for downloads, bookmarks, history, drafts or all image/audio caches.

## Important limitations

This is a foundation, not a guarantee that every route or asset works offline. Only successfully cached or prefetched data can be used offline; an uncached page needs a connection. Forum RPC responses include viewer reactions, ownership or other session-dependent fields, so they are intentionally not persisted in this shared public cache. Private account data and writes also remain online-only. Search-text queries are excluded. Some screens still fetch from other clients or hold state rather than observing the shared cache. Same-URL image/PDF replacements do not have a reliable version signal; the dashboard should publish versioned URLs for changed media. Stale public data may remain visible while offline until a successful refresh or system eviction. Avoid putting secrets into URLs or public fields.

No schema migrations or production settings are changed. Android build, WorkManager/network transitions, image cache behavior, real device offline UX, and end-to-end Supabase behavior must be tested on staging and devices before release. Core HTTP-cache tests use HTTPS MockWebServer and cover cache reuse, background refresh, failure, restart/offline behavior, eviction, and private request isolation.
