### Phase 0 — Decisions & skeleton

The acceptance ("`npm run dev` serves a shell, migrations apply cleanly, CI
green") holds. The one thing to decide:

- **P0-1 — `supabase/schema.sql` is a 9,038-line snapshot last written at
  `b06dc66`** (nine migrations ago, including all six plugin packages). It is
  not generated by any script and nothing fails when it drifts, so it is
  currently a document that lies about the schema. Three options: regenerate it
  as part of `db:push` and fail the build on drift; reduce it to a pointer at
  `supabase/migrations/`; or delete it. My preference is the pointer — the
  migrations *are* the schema, and a second copy has to be maintained to be
  worth having.

### Phase 1 — Foundation

Everything in the checklist exists and is exercised — tokens, kit, router, shell,
event bus, permission registry, navigation registry, command registry, settings
store, plugin registry, SDK, RLS, repositories, session store. Four items to
moderate, in order of how much they will cost later:

- **P1-1 — i18n (bn ⇄ en) does not exist.** *(spec §38/§39 promise it; nothing
  in `src/shared` or `src/components` provides it — the only two files that
  mention "translate" are a toast and an input.)* Today every string is an inline
  English literal, in ~15,000 lines of UI code. This is a **platform** feature,
  so its cost grows with each phase and each plugin — and every plugin screen
  already shipped would need strings extracted. Decide: build it now (a
  `t()` + catalogue + the ExtractedStrings lint), or strike it from the spec and
  the roadmap so it stops being an implied promise. I would build it now,
  because the plugin SDK can then *require* keys from plugins rather than
  discovering the problem after twelve more of them.
- **P1-2 — There is no component gallery.** Phase 1's acceptance says "every
  component in the kit has a usage example page". No such route exists. Cheap to
  add (one dev-only route rendering the kit), and it pays for itself the moment
  a plugin wants to know what to use.
- **P1-3 — Dark mode is defined but unreachable.** `src/styles/tokens.css` has a
  full `.dark` palette and a `prefers-color-scheme` block, and nothing can set
  it — there is no theme control and no settings screen (see P4-1).
- **P1-4 — The branch switcher and the `set_active_branch` Edge Function were
  never built.** *(Phase 1 checklist; no `supabase/functions/` directory exists,
  and no branch control in `sidebar.ts`/`app-shell.ts`.)* The schema is
  multi-branch (`branches`, `user_organizations`, per-branch sessions), and the
  session has `activeBranchId`, but a shop with two branches cannot switch. This
  is a **universal POS capability** (§51) and a Phase 4-era promise; it needs an
  RPC (`set_active_branch`) rather than an Edge Function, so it is small.

### Phase 2 — Core POS

Shipped: catalogue list, product form with progressive disclosure, quick add,
duplicate, POS with hold/resume, split payment, customers, receipt, register,
sales list and refunds. Four residues:

- **P2-1 — Product CSV import/export.** The CSV *engine* exists
  (`src/shared/export/csv.ts`) and is used by Reports; products cannot be
  imported or exported at all. For a shop migrating from another POS this is the
  difference between an afternoon and a week, so it is a real product gap, not a
  checkbox.
- **P2-2 — Category / brand / unit management screens.** `products-view.ts`
  reads `listCategories`/`listBrands`/`listUnits` into selects, and there is no
  screen that creates any of them. A shop cannot add a category without SQL.
- **P2-3 — Setup wizard step 7 (first product).** Onboarding is a single form:
  shop name + shop type (`onboarding-view.ts`, two fields). Phase 2's checklist
  says step 7 adds the first product; there are no numbered steps at all.
- **P2-4 — Two acceptance criteria are *claims*, not results.** "A cashier
  completes a sale with keyboard only, in under 10 keystrokes" is asserted in a
  comment in `pos-view.ts:6`; nothing counts keystrokes. "Holding a sale,
  serving another customer and resuming works across a logout/login" has no test
  (the hold tests never sign out). Both are cheap to prove — a keystroke counter
  in the POS harness and a session-reset held-cart test — and both are exactly
  the kind of thing that quietly breaks.

### Phase 3 — Inventory

Verified by construction: ledger immutability, `before + delta = after` on every
row (randomized property test), balances equal the sum of movements, valuation
equals Σ(balance × avg_cost) in both Postgres and on screen. The single deferral
is explicit and lands in Phase 7 as `stocktake`. **No modification proposed.**

### Phase 4 — Business management

Purchases → receive → supplier balance, expenses, returns (full/partial/item),
store credit, register session report, and the audit trail attached to eighteen
tables. All asserted in the validator and over HTTP. One omission:

- **P4-1 — Staff, Roles and Settings were never built, and the sidebar still
  says they arrive in "Phase 4" — a phase marked complete.**
  *(Evidence: `src/main.ts` registers dashboard, pos, products, stock, sales,
  customers, suppliers, purchases, expenses, register, audit, analytics, reports,
  plugins — and not `/users`, `/roles` or `/settings`; the gap becomes a
  `placeholderView` whose text comes from `placeholder-view.ts:35` and friends.)*

  This is the most consequential finding in the audit, because it is *not just
  UI*: `contracts/api-contract.json` contains no RPC that updates an
  organization, creates a staff account, invites a user, or assigns a role. So:
  - a shop **cannot change its own name, currency, timezone, tax defaults or
    receipt footer** after provisioning;
  - a shop **cannot add a second user** — RBAC exists (roles, `user_roles`,
    permissions, seeds) but the only writer is `provision_organization` (the
    owner) and direct SQL;
  - "multi-user RBAC" is therefore schema-complete and workflow-incomplete.

  The work is three new server functions (`update_organization`, `invite_user` /
  `set_user_roles`, `set_active_branch` — the last covering P1-4) plus three
  screens. That is Phase-4-sized, and it is the difference between a POS one
  person can use and one a shop can.

### Phase 5 — Analytics

One engine, one dashboard call, eleven reports, CSV/print/PDF, and the §56
questions on the dashboard. The acceptance criteria are asserted by
`tools/mobile-audit.mjs` (164 checks) against a real browser at phone width. **No
modification proposed in this phase itself** — but note the audit's own
reproducibility gap (P8-1), and that the CSV work does not extend to the
catalogue (P2-1).

### Phase 6 — Plugin hardening

`plugin_enable` as `SECURITY DEFINER`, checksummed and transactional migrations,
the tenancy guard on every package table, the world-grant closure on every
function a package creates, quarantine + retry, the impact preview, the settings
schema, and the §51 boundary lint. All green, and the "careless plugin" fixture
in the validator proves the grant closure by *trying* it. **No modification
proposed.**

### Phase 7 — Industry plugins

Six of fourteen capability plugins shipped (`variants`, `batch-expiry`,
`serial-numbers`, `warranty`, `weight-scale`, `loyalty`), each meeting the
acceptance test: wizard defaults come from the taxonomy, the promoted-field
reader works (`c3b9f20`), reports reach the core screen (`a15cf1c`), and
**none of them touched `src/features/`**. Two structural items before the
industry bundles begin:

- **P7-1 — Industry bundles have no acceptance harness.** The four acceptance
  bullets exist for capability plugins; for the twenty industry bundles there is
  no machinery at all. Without one, "Pharmacy works" is an assertion. I would add
  `tools/industry-audit.mjs`, driven by `data/shop_categories.json`: for each
  leaf the wizard can create, assert (a) provisioning with that `shop_type`
  yields the profile's default plugins, (b) the promoted fields appear in the
  product form and the rest stay in Advanced, (c) at least one report returns
  rows. That is one script that turns twenty claims into twenty results.
- **P7-2 — `loyalty-lite` ships to shops with no SQL file on disk.** *(The live
  database has `loyalty-lite/001_accounts.sql` (md5 `41a7a0ef…`) and
  `002_functions.sql` (md5 `8d9acb33…`) as package rows; `supabase/plugins/` has
  no `loyalty-lite/` directory.)* The validator's "every plugin SQL file is
  embedded byte for byte" check walks **disk → migration**, so the reverse drift
  is invisible. Two fixes, and they are a decision:
  1. **Reconstruct** the two files from the database (md5-checkable), commit
     them, and add the missing direction to the validator: a package row whose
     file is not on disk fails. `loyalty-lite` stays as the SDK's smallest
     complete example.
  2. **Retire** `loyalty-lite` now that `loyalty` is the production plugin — it
     would remove a second points implementation from every shop's catalogue,
     and the teaching job passes to `weight-scale` (which the SDK doc already
     points at). This needs your call because the docs use it as "the shape
     without the policy".

### Phase 8 — Offline & Android

IndexedDB data source, write queue + sync engine, the client reference that
makes a resend return the stored sale, conflict policy written down, sync
indicator, generated contract, and a Kotlin core that is *executed* twice —
against a fake and against the live project. **Met.** One gap:

- **P8-1 — `tools/mobile-audit.mjs` cannot run on a fresh clone.** It imports
  `puppeteer`, which is not in `package.json` (its own header says
  `npm install --no-save puppeteer`). So the 164-check phone audit — the thing
  that verifies Phase 4 and Phase 5 acceptance — is unavailable to anyone who
  clones the repo, and unavailable in this sandbox after a dependency reset. Add
  it as a devDependency (or an `optionalDependencies` entry with a skip message).

## 4. What needs your decision

1. **P7-2** — reconstruct `loyalty-lite`'s SQL on disk, or retire the plugin now
   that `loyalty` is the production one?
2. **P1-1** — build i18n (bn ⇄ en) as a platform feature now, before twelve more
   screens and eight more plugins exist, or remove it from the spec?
3. **Order** — do you want Tier 1 (½ week, pure risk reduction), Tier 2 (spec
   residue, ~2 weeks), or the next Phase 7 plugin next?
4. **T3-4** — how much of the feature-view test coverage do you want, given the
   validator and the phone audit already cover the paths a shop actually walks?

## 5. My recommendation

**Tier 1, then T2-1/T2-2, then back to Phase 7.** The reasoning: Tier 1 is days
of work that removes a destructive-command footgun, makes two acceptance claims
real, and closes the drift hole that hid P7-2. T2-1 and T2-2 close the only two
places where the product's own sidebar and its own spec promise something a shop
cannot do — and both are *prerequisites* for selling this to a shop with more
than one employee or more than one branch. Everything else (i18n, the gallery,
the gallery's dark mode, feature-view tests) is additive and can wait until the
capability plugins are done, with one exception: i18n gets more expensive every
week it is deferred, so if it is ever going to happen, the cheapest moment is
now.
