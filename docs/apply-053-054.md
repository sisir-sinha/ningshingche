# Applying migrations 053 and 054

Two migrations are written, tested against PGlite (218/218 behavioural checks) and
committed, but not yet applied to the live database:

| File | What it does |
| --- | --- |
| `supabase/migrations/20260927_053_delete_product.sql` | A real `delete_product` RPC. Refuses a product that appears on a sale, return or purchase (naming the count, so the client can offer Archive instead); otherwise deletes it with the rows that only describe it. |
| `supabase/migrations/20260927_054_product_sku.sql` | `assign_product_sku()` + the `products_assign_sku` trigger. Fills a blank SKU as `MIN-0007` (three ASCII letters from the name, four-digit sequence from `public.next_sequence`); falls back to `SKU-0001` for an all-Bangla name. |

Neither touches existing data. 053 only adds a function; 054 adds a function and a
`before insert` trigger that fires when `sku` is null.

Pick **Route A** (the repo's own pusher — recommended, it records the migrations in
the ledger) or **Route B** (paste the SQL, 60 seconds, no ledger entry).

---

## Route A — `npm run db:push` from your machine

### 1. Get the database password

Supabase Dashboard → your project → **Project Settings → Database**.

This is *not* your Supabase account password — that's the one that failed when I
tried. The database password is shown once at project creation. If you don't have
it, click **Reset database password** on that page and copy the new one.

Resetting is safe: it does not touch data, and nothing in Mekholi uses it. The app
authenticates with the anon key in `.env`; this password is only for direct SQL
connections like this one.

### 2. Create `.env.db` in the repo root

It is already in `.gitignore`, so it will not be committed.

```ini
MEKHOLI_DB_HOST=aws-0-ap-south-1.pooler.supabase.com
MEKHOLI_DB_PORT=5432
MEKHOLI_DB_USER=postgres.tjhodyveonlzabjaaino
MEKHOLI_DB_PASSWORD=<the database password>
MEKHOLI_DB_NAME=postgres
```

Everything except the password is already confirmed correct — I probed every
Supabase pooler region and `aws-0-ap-south-1` is the only one that recognises the
tenant `postgres.tjhodyveonlzabjaaino`; the rest answer *"tenant/user not found"*.

Two details that matter:

- **Port 5432, never 6543.** Migrations run DDL and `alter publication`, and
  transaction-mode pooling (6543) breaks both.
- **Use the pooler host, not `db.<ref>.supabase.co`.** The direct host is
  IPv6-only. It will work from a home connection with IPv6; it fails with
  `ENETUNREACH` from anything IPv4-only.

If your password contains `#`, quote it or the `.env` parser reads the rest of the
line as a comment.

### 3. Look before you leap

```bash
npm install          # the pusher needs the `pg` package
npm run db:push -- --status
```

Expect a list of applied migrations, with `20260927_053_delete_product` and
`20260927_054_product_sku` marked pending. If 001–052 also show as pending, stop —
that means the ledger table `supabase_migrations.schema_migrations` is empty and a
push would re-run everything. Tell me and I'll walk you through backfilling it.

### 4. Apply

```bash
npm run db:push
```

Then confirm nothing is left:

```bash
npm run db:push -- --status
```

### 5. Check it actually works

In the Dashboard SQL editor:

```sql
-- 054: the trigger is armed
select tgname from pg_trigger where tgname = 'products_assign_sku';

-- 053: the RPC exists
select proname from pg_proc where proname = 'delete_product';
```

Or just use the app: **Quick add** a product with the SKU box empty and the list
should show a real code instead of a dash. Then delete a product that has never
been sold — it should disappear; delete one that has, and you should be told how
many documents reference it and offered Archive.

## Route B — paste the SQL

If you'd rather not deal with the password:

1. Open `supabase/migrations/20260927_053_delete_product.sql` in the repo.
2. Copy the whole file into Dashboard → **SQL Editor** → **Run**.
3. Repeat with `supabase/migrations/20260927_054_product_sku.sql`.
4. Run the two verification queries in step 5 above.

Order matters only in that 053 should go first; they are independent otherwise.
Both are written to be re-runnable (`create or replace`, and 054 drops its trigger
before creating it), so running one twice is harmless.

The one cost: `supabase_migrations.schema_migrations` won't know they ran, so a
later `npm run db:push` would try them again. Harmless for these two, but if you
want the ledger straight afterwards, run:

```sql
-- The pusher keys the ledger on the filename minus `.sql`, so these strings
-- must match exactly or it will try the migrations again anyway.
insert into supabase_migrations.schema_migrations (version, name)
values
  ('20260927_053_delete_product', '20260927_053_delete_product'),
  ('20260927_054_product_sku',    '20260927_054_product_sku')
on conflict (version) do update set applied_at = now();
```

## If something goes wrong

| Symptom | Cause |
| --- | --- |
| `password authentication failed for user "postgres"` | Wrong password — it's the database password, not the account one. Reset it. |
| `tenant or user not found` | Wrong region in the host, or the user is missing the `.<project-ref>` suffix. |
| `ENETUNREACH … :5432` | You used `db.<ref>.supabase.co` (IPv6-only) instead of the pooler host. |
| `Cannot find package 'pg'` | Run `npm install` first. |
| `prepared statement … already exists` | You're on port 6543. Switch to 5432. |
