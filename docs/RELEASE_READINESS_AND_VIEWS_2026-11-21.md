# Song / forum views and Play release assessment

Assessment date: 2026-11-21. This is an audit of the local source and selected read-only production database facts, not a certification of Play approval or a production end-to-end test. The app remains versionName 1.1 / versionCode 36 until release readiness and the next available Play versionCode are established.

## What was checked

- Production `content_view_record`, `forum_discussion`, `music_valid_seconds` and visit-window functions, current aggregate event counts, grants and RLS; no production rows or schema were changed.
- Song player metering and submission path, forum screen and thread RPC, local dashboard aggregation and configuration, release configuration, policy pages and official Google Play requirements.
- Full checked-in Node suite: 639 passed, 13 skipped. This includes source-pattern tests, not Android integration tests. Two standalone Kotlin unit tests cover fractional listening-report arithmetic. Four changed Kotlin files passed a parser-only check.
- No signed bundle was built; Android SDK, JDK 17+, release signing credentials, Play Console and an Android device were unavailable in this workspace.

## Views: findings and local fixes

- Live `content_views` held 46 forum and 183 music event rows at the time of inspection, spanning guest and signed-in viewers. Six music event rows referred to deleted/nonexistent tracks; forum events all had a current discussion. These historical rows should not be silently deleted without a retention/analytics decision. Aggregation of owned content independently matched event rows in the earlier read-only check. Views recorded before the event model can make stored item counts differ from event totals.
- The server counts one view per viewer/content in a 30-minute window; song count eligibility is 30 seconds or half a track shorter than one minute. Additional reported song seconds accrue within that window. A viewer key is an account or device identifier, not proof of a unique human. Creator dashboard music minutes are listening to owned tracks, not a listener's own total; older songs without an owner are not credited.
- **Fixed locally, not deployed/device-tested:** a thread load that failed initially can request the view again on refresh; once a response succeeds, later refreshes do not count that destination again. If a response was lost after server commit, server deduplication ordinarily prevents a duplicate forum view.
- **Fixed locally, not deployed/device-tested:** closing the song player flushes eligible accumulated time before the ticker becomes invisible and resets its meter; whole-second reporting preserves the subsecond remainder. A missing callback no longer advances the reported marker.
- **Still unresolved:** music sends each interval as a separate asynchronous, non-idempotent request, advances the local marker before the network result, and silently ignores failures. Network loss can lose counts/seconds; requests can arrive out of order; a short tail that arrives before the threshold report may be discarded. A naive retry risks double-counting seconds if the server committed but the response was lost. A robust change needs ordered, durable delivery and a server-issued or client-generated idempotency key committed atomically with seconds, while respecting public-only cache and user/account identity boundaries. Design and test this against staging before rollout. The 400 ms ticker also loses small position intervals during pauses, transitions and end-of-track; no claim of sample-accurate accounting is made.
- **Still unresolved:** server visit deduplication uses a lookup followed by an insert with no per-visit lock or unique constraint. Concurrent requests may insert duplicate views. The public RPC trusts client-supplied listening time and guest device IDs, so counts are not fraud-resistant, and the recorder does not establish that every supplied target exists and is publicly viewable before recording. Design an atomic, backward-compatible server migration; verify authenticated, anonymous, concurrent, unpublished/nonexistent, and response-lost retry cases in staging. Do not reset or rewrite historical counters without a backup and explicit decision.
- `content_views` has RLS enabled and no policies, but live role grants include table privileges for anon and authenticated, including TRUNCATE (which is not subject to row-level security). A normal PostgREST table route does not itself expose SQL TRUNCATE; nevertheless review/revoke unnecessary table grants with staging tests of RPCs and dashboard, and evaluate whether untrusted roles have any direct SQL path. Do not assume RLS alone protects every operation.
- Live `forum_discussion_rows` is the older unfiltered definition; migration 047 adds visibility/block filters but is not deployed. Source safeguards are not the same as live protections.

## Play readiness: blocking / unverified work

1. **Production/staging:** prerequisite Terms and article submission RPCs are missing in production, and local profile/comment/book and UGC migrations are not deployed. Validate every prerequisite and migration in a production-like staging project with real JWT/RLS and a verified restorable production backup before a planned release. Validate the real third-party PDF upload path and admin book-review workflow; pending public links can be accessible to anyone with the URL.
2. **UGC safety:** finish and verify effective terms acceptance, reporting, blocking, moderation, visibility and deletion/retention paths for all applicable content, not only source-level UI. Set up actual response/moderation ownership. Google requires robust ongoing moderation and UGC terms, reporting and blocking: https://support.google.com/googleplay/android-developer/answer/9876937?hl=en.
3. **Privacy and deletion:** on this check, `https://ningshingche.com/privacy.html`, `/terms.html` and `/account-deletion.html` returned HTTP 404. The app has deletion code and the live `delete_my_account` RPC exists, but its real end-to-end behavior and associated-data retention must be audited; account-view identifiers and third-party uploads need particular attention. Publish working, accurate legal and external deletion-request pages and complete Data safety. Google requires in-app and external account deletion request paths: https://support.google.com/googleplay/android-developer/answer/13327111?hl=en.
4. **Build/sign/device:** install a supported JDK and Android SDK, execute a clean release compilation and tests, create and verify a correctly signed AAB with the legitimate upload key, and test an installed release on representative Android devices including Android 16 and a 16 KB environment. Check every native library in the final bundle, not just the PDF dependency. The configured targetSdk 36 meets the relevant August 2026 mobile target rule, but does not establish full compliance: https://support.google.com/googleplay/android-developer/answer/11926878?hl=en.
5. **Play Console:** confirm the package, highest historical versionCode, Play App Signing/upload key and SHA-1 for Google Sign-In, testing-track requirements applicable to this developer account, review access instructions, Data safety, privacy/deletion URLs, content rating, target audience, any applicable foreground-service declaration/video, store listing and rights. These are unverified without Console access. Never guess the next versionCode.
6. **Functional regression on device and staging:** guest and registered fresh thread views; repeated opens, refreshes and response loss; music below/above threshold, short/unknown-duration tracks, pause, seek, track switch, repeat, dismiss/reopen, offline/reconnect, concurrent/out-of-order requests and process death; verify both public totals and contributor dashboard figures. Also verify login/recovery, comments, submission/review, media/PDF, offline cache and deletion. Password-recovery link versus six-digit-code flow remains an identified mismatch.
7. **App links:** `https://ningshingche.com/.well-known/assetlinks.json` returned 404; automatic Android App Link verification requires a correctly hosted, signed-certificate-matching assetlinks file.
